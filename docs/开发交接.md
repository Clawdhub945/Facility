## 0. 最新进展（1.2.0）：自定义建筑外观**已跑通**

**结论先说**：mod 通道**可以**给新建筑换自定义模型，但**不能新建 prefab**，
只能「复用游戏已有 prefab + 运行时替换贴图」。

### 0.1 正确做法（作者侧验证过，本项目也已复现成功）

```
stuff.json : prefab = "workbench"（游戏已有）, stuff_img_on_map = "super_factory_0"（我们新增的名字）
build.json : class_name = "FacilityGatherersHut", cellw=3, cellh=2
textures.xml: <Image file="super_factory_0.png" action="add" anchor="0,0" />   ← add，不是 replace
DLL        : Harmony 挂 BuildHelper.DoBuildFacility 的 Postfix →
             把刚建好的那栋建筑的 sp_body.sprite_id + 所有 SpriteRenderer.sprite 换成我们的图
```

### 0.2 两套渲染都要改，否则贴图是透明/不显示

| 渲染系统 | 认什么 | 改完必须做什么 |
|---|---|---|
| `MySpriteRenderer`（游戏自绘批渲染） | **只认 `sprite_id`**，完全忽略 `sr.sprite` | `SetActive(false)` + `SetActive(true)` 强制刷新 |
| 原生 `SpriteRenderer` | 认 `sprite` | 直接赋值 + `enabled = true` |

实测日志（成功时的样子）：
```
[Facility] 贴图已加载 super_factory_0.png 96×73 ppu=64
[Facility] 自定义外观贴图：4/4 个朝向已加载（ppu=64）
[Facility] sprite_id ← super_factory_0
[Facility] 超级生产所外观已替换（朝向 0：自定义渲染 1 个 / 原生渲染 1 个）
```
用户实测：**紫色工作台模型（自定义贴图）已经出现在地图上** ✔

### 0.3 试错记录：以下三条路**全部失败**（别再走）

| 做法 | 结果 |
|---|---|
| `textures.xml action="add"` + stuff.json 写**新 prefab 名** | 放置时 `NullReferenceException`（游戏按名字找不到预制体） |
| `action="replace"` 覆盖游戏已有贴图名（`workbench_0`） | 洋红探针实测**不生效**（世界里 0 个洋红像素，只有工具栏 14 个） |
| DLL 运行时自造 GameObject 当 prefab + 拦 `PrefabManager.Get/Create` | 贴图/prefab/图标都建成功了，但游戏**从不请求自造的名字**（日志抓到的一直是 `workbench_0`），模型解析受 `class_name` 约束 |

### 0.4 其他关键点

- **贴图尺寸**：游戏一格 = 64 像素。3×2 建筑图约 96×73（正面）/ 64×118（竖版），
  `pivot` 用左下角 `(0,0)`、`pixelsPerUnit = 64`（= 每格像素数）。
  4 个朝向对应 `_0.._3`，必须都提供，否则旋转后没图。
- **本地 mod 必须有 `About/About.xml`**（官方 mod 结构要求）。
  `C:\TerritoryModTest` 里放 `About/About.xml` + `About/Preview.png`（637×658）。
- **`BuildHelper.DoBuildFacility`** 是私有方法，用 `AccessTools.TypeByName("BuildHelper")` +
  `AccessTools.Method(t, "DoBuildFacility")` 找。

## 0. 0.4.0 这轮做了什么（先看这个）

| 改动 | 为什么 | 实测结论 |
|---|---|---|
| **换日判据改用 `Clock.Days`** | 原先用 `Clock.Now.Year*10000+MonthInYear*100+DayInMonth`，**一天之内会反复给出不同「日期」** | 旧日志里 3 座建筑刷了 **512 次**「新的一天」，把建筑袋子灌爆。改 `Clock.Days` 后严格一天一次（测试台断言覆盖） |
| **产出加 `Facility.RecordProduct`** | 只 `AddStuff` 只进袋子，不进产量统计 | 窗口「今年产量」现在列出 原木/石料/红宝石/秘银矿（截图实证），额外产品动态选中的产品也会进记录区 |
| **Defs 补齐额外产品 blueprint 行** | 蓝图行是产品数据键总开关 | 5 行：604001/605001/616001/616002/612001，`formula_id` 槽位 40 起 |
| **同日防重** | 万一日期判据再退化，同一建筑一天只能发一次 | 内存 `HashSet<int> _producedToday`，换日清空 |
| **`_tools/autotest.py` 全自动测试台** | 需要「全自动操控电脑」做回归 | 见 §10，实测能无人值守跑完「启动→进档→定位建筑→点窗口→断言 cfg/日志」 |
| **下拉框（0.5.0）** | 原来是「点一下循环切一个」，用户要求真下拉 | 标题条展开 4 项候选（无/铁矿/秘银矿/红宝石），点哪项选哪项；实测展开→选中→写 cfg 全通（日志 `下拉框展开（3 个候选）` → `下拉框选中 0（无）`） |
| **建筑外观可换（0.5.0）** | 用户要求改预制体 | `_tools/make_defs.py --appearance <预设>`，5 种预设实测都能进档、模型真的换了 |

> ⚠ `Clock.Now` 仍可用于读年月（游戏自己也这么读），但**判日一律用 `Clock.Days`**：
> 游戏源码 264 处判日全是 `Clock.Days`（`Animal.cs:571`、`Npc.cs:9061`、`Facility.cs:1500`…），
> 存档 `summary.sav` 里的 `days` 字段就是它。

### 0.1 下拉框实现要点（0.5.0）

原生 `Dropdown` 在本游戏点不开（见 §7），所以是**自己拼的下拉框**：

- **标题条**（`FacilityExtraProductSelector`）：显示当前选择，点一下展开/收起
- **选项面板**（`FacilityExtraProductDropdown`）：紧跟标题条下方，行名 `Row_<物品id>`
  （`Row_0` = 「无」），当前选中行高亮 + 前缀 `●`
- 每个可点对象**同时挂 `Button.onClick` 与 `EventTrigger(PointerClick)`**：
  游戏的输入派发是手写的，两条路径都挂才稳
- ⚠ **同一帧内要防重复派发**：`ExecuteEvents.Execute(go, …, pointerClickHandler)`
  会把 Button 和 EventTrigger **两条回调都触发**，于是「展开」被连按两次变成「展开又收起」
  （日志实证：展开→收起→展开→收起）。用 `Time.frameCount` 去重解决。
- F8 测试钩子（`FacilityWindowUi.TestClickSelector`）走「展开 → 点下一项」，不依赖 OS 坐标

### 0.2 建筑外观（预制体）怎么改（0.5.0）

建筑外观由 `Defs/stuff.json` 的三个字段决定，**三者必须配套**：

| 字段 | 作用 | 例子 |
|---|---|---|
| `prefab` | 场景里的 3D 模型（也进 `GoName = prefab + guid`） | `workbench` |
| `stuff_img` | UI 图标 | `ui_105010` |
| `stuff_img_on_map` | 小地图图标 | `workbench_0` |

```bash
python _tools/make_defs.py --appearance 制造台 --deploy   # 可选：采集营地/磨坊/交易台/制造台/熔炉
python _tools/test_appearance.py                          # 逐个试：能否进档 + 模型像素对比
```

实测 5 种预设全部可用（进档 3.0~3.1s，`goName` 随预设变化，与基准图建筑区像素差 6~8%）。
**默认选了「制造台」（`workbench`）**——它是产线建筑，最贴「综合生产所」的定位；
尺寸 3×1 与占地 3×3 不同，若在意占地框贴合可换「交易台」（3×3）。

> ⚠ 换外观只动 Def 数据，**不用改代码**；改完要**重新进档**（Defs 在 LoadData 时读）。
> `_tools/test_appearance.py` 会自动重启游戏+进档+截图对比。

## 2. 环境、构建、部署（照做即可）

### 2.1 构建

```bash
cd /c/AI/mod/Facility
MSBuildEnableWorkloadResolver=false dotnet build -c Release
```

> ⚠ **`MSBuildEnableWorkloadResolver=false` 必须加**：这台机器 `dotnet` SDK 10.0.202 的
> 工作负载清单损坏（`工作负载集版本 10.0.203 缺少清单`），不加这个环境变量会直接 MSB4242 报错。
>
> ⚠ **不要用 `| tail -2` 之类的截断看构建输出**——本次开发中因此连续多次「以为构建成功、
> 实际全程编译失败」，DLL 停在旧版本，白白排查了很久。至少 `grep -E "error|个错误"`。

构建后 csproj 的 `PostBuild` 目标会自动复制 DLL 到 `C:\TerritoryModTest`。

### 2.2 部署链路（关键）

```
构建 → C:\TerritoryModTest\Facility.dll + Defs\*.json
        ↓ 游戏启动时「镜像同步」
     BepInEx\plugins\1006\Facility.dll + Defs\*.json
```

- `C:\TerritoryModTest` 是**游戏自带的本地测试目录**，启动时把整个目录镜像进 `plugins/<某个槽位>`
  （本项目实测是 **1006**；`1005` 是创意工坊版 JianZhu 的槽位）。
- **直接放 `BepInEx\plugins\自建文件夹` 会被游戏启动时删掉**，必须走 TerritoryModTest。
- 镜像同步发生在**游戏启动时**，所以改 DLL/Defs 后必须**重启游戏**才生效（Defs 也是，见下）。

### 2.3 改 Defs 后怎么生效

- Defs 是**进存档时**由 `D.LoadData` 读取的 → 改完 Defs 后**重新进入存档**即可，不必重启游戏。
  （但建造菜单 `BuildMenuGroup` 的装配是进程启动时做的，**动了 tech.json 必须重启游戏**。）

### 2.4 自动化进存档（开发效率关键）

## 3. 逆向结论：这个游戏的 Mod Def 体系（**最重要的一节**）

游戏的官方 Mod 通道：`BepInEx/plugins/<任意文件夹>/Defs/<表名>.json`，
文件名（去扩展名）= 表名，内容是 JSON 数组，和官方表同一个加载器解析。

**关键教训：一座新建筑光有 stuff+build 是远远不够的。** 我们逐个撞出来缺什么：

| 表 | 缺了会怎样 | 必填要点 |
|---|---|---|
| `stuff.json` | 物品/设施不存在 | `stuff_id`、`prefab`、`stuff_img`、`stuff_img_on_map`、`effect_value` |
| `build.json` | 建筑不存在 | `id`、`class_name`(如 `FacilityGatherersHut`)、`cellw/cellh`、`menu_group`、`have_worker` 等 |
| `tech.json` | **建造菜单里完全不显示** | `txt_id` 是**分类段号**，必须与 `menu_group` 配对（见下） |
| `career.json` | **窗口没有工人控件、永远分不到工人** | 每个 `data_id` 组里 `is_main_facility` 只能有一个为 1 |
| `blueprint.json` | **窗口整个退化成占位值 + 主循环每帧抛异常** | 产品行 `product_id` + `formula_id`（官方惯例 `product_id*100+序号`） |

### 3.1 tech.json 的 `txt_id` = 分类段号

实测段号与 `menu_group` 的对应关系：

| txt_id | menu_group | 分类 |
|---|---|---|
| 100 | 0 | 初始 |
| 200 | 1 | 住所 |
| **300** | **2** | **食品**（本项目用） |
| 3700 | 3 | 制造 |
| 1500 | 4 | 物流 |
| 600 | 7 | 路桥 |

`tech_id=0` = 免科技。用错段号 → 建筑不出现在目标分类（我们一开始抄大通铺用了 200，菜单里死活找不到）。

### 3.2 career.json = 工人系统总开关

- 游戏里 `Facility.GetOriginalWorkPosCount` 会查 `D.career_dic_with_facility_id_as_key[stuff_id]`，
  查不到 → 工位数 0 → 窗口不渲染工人区、永远没人来（我们最初窗口就是个只读模板）。
- `npc_type` 决定职业（8=采集者）。多设施共用同一职业是**官方常态**（两块农田共用一个 farmer），
  所以我们直接复用采集营地 105006 的采集者职业行。
- ⚠ **`is_main_facility`：同一 `data_id` 组里只能有一个主设施**。
  我们照抄的行也是 1 → 采集者职业出现两个主设施 → 人手 DB 混乱（当时表现为窗口 99/99 不可交互）。
  必须置 **0**。
- `manpower_limit` 是基础工位数，但实际"原始工位数"被我们用 Harmony 补丁接到 cfg 了（见 §4）。

### 3.3 blueprint.json = 产品记录 / 数据键总开关（最阴的一个）

`FacilityHuntingCabin.GetProductDataKeyList(stuff_id)` 会按设施 id 查蓝图字典，**缺行直接抛 KeyNotFoundException**。

这一个异常会连锁炸掉：
- `WindowWorkFacility.SetInfo` 整条绑定链 → 窗口全变预制体占位值
  （工人数 99/99、库存空、今年/去年产量是假数据「原木四字 98」）
- `FacilityWork.IsReachLimit` 在 `NpcTaskHelper.Tick`（主任务循环）里**反复抛** → 工人领不到任务

我们加了 604001/605001 两行后，以上全部恢复正常。
**新建筑只要 `have_worker` 且想有产出，就必须有 blueprint 行。**

0.4.0 起蓝图行扩到 5 行（原木/石料/铁矿/秘银矿/红宝石），由 `_tools/make_defs.py` 的
`DEFAULT_PRODUCTS` + `DEFAULT_EXTRA_CANDIDATES` 生成，`formula_id` 槽位从 40 起
（`formula_id = product_id*100 + 槽位`，槽位在同一设施内唯一即可）。

### 3.4 产量记录：只 `AddStuff` 不进「今年/去年产量」

窗口里的「今年产量/去年产量」读的是 `Facility.ProductRecordBagThisYear / LastYear`，
**唯一写入入口是 `Facility.RecordProduct(stuff_id, count)`**（官方源码 `Facility.cs:71`，
它同时写设施自己的记录袋与全局 `bag_product_this_year`；年底 `DoOnNewYear` 把今年滚成去年）。

```csharp
f.AddStuff(sid, count);        // ① 进建筑袋子（搬运工再搬进仓库）
f.RecordProduct(sid, count);   // ② 进产量统计（窗口「今年产量」）
```

两者都要调。0.4.0 之前只调 ①，所以记录区只有 blueprint 声明的、且被别的东西记过的产品。

## 4. 代码结构

| 文件 | 职责 |
|---|---|
| `Plugin.cs` | 入口。绑定 cfg、注册 `FacilityComponent`、`PatchAll()`。含 `LogV`（详细日志门控）、`ParseProducts`、`ParseExtraCandidates`、`SetExtraProduct` |
| `FacilityComponent.cs` | 主线程服务循环（1.5s）：Reload cfg → 检测换日（**`Clock.Days`**，0.4.0 修正）→ 每座建筑按 `工人数 × 产出表` 调 `AddStuff` 入袋 + `RecordProduct` 记账；含同日防重 `_producedToday` |
| `FacilityWorkPosPatch.cs` | Harmony Postfix `Facility.GetOriginalWorkPosCount`（仅 105040）→ 返回 cfg「每座最大工位数」，使窗口 +/- 可调人数 |
| `FacilityWindowUiPatch.cs` | 挂 `WindowGatherersHut.SetInfo` + `UpdateState`/`ShowWindowTip` → 调 `FacilityWindowUi.Apply` |
| `FacilityWindowUi.cs` | 窗口 UI 定制：改写文案 + 构建/刷新「额外产品」选择条（原生 uGUI `Button`，点击循环）；详细模式下上报选择条屏幕坐标供自动化点击 |
| `Defs/*.json` | 5 张表（stuff/build/tech/career/blueprint），**由脚本生成，不要手改** |
| `_tools/make_defs.py` | 从官方表 `C:\AI\领地部分源码(AI注释)\ExtraData` 拷贝模板行生成 Defs；`--deploy` 部署到 `C:\TerritoryModTest\Defs` |
| `_tools/autotest.py` | **全自动操控电脑的测试台**（截图/鼠标/键盘/进程/读档/日志/HTTP），见 §10 |
| `_tools/e2e.py` | 端到端回归测试：自动启游戏→进档→定位建筑→点开窗口→点选择条→断言 cfg+日志，逐项 PASS/FAIL |
| `_tools/click_selector.py` / `probe_xy.py` | 单点调试：点选择条后读 cfg 验证；把光标放到指定客户区坐标并画准星截图 |

### cfg 键

```ini
[生产]
每人每日产出 = 604001:10,605001:10      # 物品id:每人每日数量，逗号分隔
每座最大工位数 = 10                       # 窗口 +/- 上限（1-25）
额外产品候选 = 616001:铁矿,616002:秘银矿,612001:红宝石
额外产品 = 0                              # 0=无；由窗口选择条写入
额外产品每日数量 = 10
[调试]
日志详细模式 = false                      # 打开后 LogV 的详细日志才输出
```

### 关键游戏 API（本项目已实测可用）

```
Clock.Days                                      # ★ 游戏日计数（判日唯一正确来源，官方源码 264 处都用它）
Clock.Now.Year / .MonthInYear                   # 年月（⚠ 不要用它拼「日」判日，见 §0）
Facility.stuff_id / .guid / .is_build_finished / .npc_list  (List<Npc>，工人表)
Facility.AddStuff(stuffId, count)               # 入袋（搬运工会自动入库）
Facility.RecordProduct(stuffId, count)          # ★ 进「今年产量」记录（窗口记录区唯一数据源）
Facility.GetWorkPositionCount / GetOriginalWorkPosCount / GetWorkerNpcCount
D.Ins.career_dic_with_facility_id_as_key        # 职业表（工人系统）
WindowGatherersHut.SetInfo / UpdateState / ShowWindowTip
```

> 找 interop 符号的可靠姿势：`Assembly-CSharp.dll` 里方法名是**拼进一个长字符串**的
> （`NativeMethodInfoPtr_RecordProduct_Public_Void_Int32_Int32_0`），
> 直接用 ASCII 正则 `[A-Za-z_][A-Za-z0-9_]{2,80}` 扫，不要用 UTF-16 搜方法名（会找不到）。
> 例：确认 `Clock.Days` 可用的证据 = `NativeMethodInfoPtr_get_Days_Public_get_Int32_0`。

窗口内已知控件名（勘察得来，用于 UI 定制）：
`txt_forest_coverage_rate`、`txt_tip`、`txt_title`、`txt_num`、`txt_this_year`、`txt_last_year`、
`txt_this_manpower`、`txt_str`；容器 `content_area`；`window_prefab = window_gatherers_hut`。
（另外 interop 里还有 `txt_this_year_harvest` / `txt_last_year_harvest` 一组，属于别的设施窗口。）

## 10. 全自动操控电脑做测试（0.4.0 新建，重点）

一套纯 Python（**只用标准库 + Pillow，不需要 pyautogui/pywin32**）的测试台：`_tools/autotest.py`。
一条命令跑完整回归：

```bash
python _tools/e2e.py            # 自动：启游戏 → 进最新档 → 定位建筑 → 点开窗口 → 点选择条 → 断言 cfg/日志
python _tools/e2e.py --no-load  # 已在存档里时跳过读档
```

`e2e.py` 会逐项打印 `[PASS]/[FAIL]`，退出码 0/1。当前覆盖 11 项：
mod 加载 → HTTP 就绪 → 进档 → 建筑存在 → 窗口打开 → 选择条坐标 → 真点击改 cfg →
F8 钩子点击改 cfg → 换日产出 → **同一天不重复产出（回归断言）** → 产出数量 = 工人数×每人数量。

### 10.1 Win32 输入：这四条是踩坑换来的

| 事项 | 结论 |
|---|---|
| **移动光标** | 必须用 `user32.SetCursorPos`。**`SendInput` 的绝对坐标移动在本机会被静默吞掉**（SendInput 返回 1、光标纹丝不动）——一开始就是被这个坑住，误以为「游戏不吃合成输入」 |
| **点按键** | `mouse_event(LEFTDOWN/LEFTUP)` 正常。真点击 = `SetCursorPos` + `mouse_event`，且游戏窗口必须在前台（`SetForegroundWindow`） |
| **键盘** | 两个都行：`keybd_event`/SendInput 给游戏，`PostMessage(WM_KEYDOWN)` 给 IMGUI（UnityExplorer 认这个） |
| **中文文本** | `WM_CHAR` 只能打 ASCII；中文走剪贴板：`OpenClipboard`+`GlobalAlloc`+`SetClipboardData(CF_UNICODETEXT)`，再发 Ctrl+V |

### 10.2 截图：用哪个 API 决定坐标准不准

- **标定坐标/做像素断言 → 必须用「全屏 GDI 抓取 + 按客户区裁切」**（`autotest.client_grab`）。
- **不要用 `PrintWindow` 标定坐标**：实测它抓到的帧与客户区**有偏移**，据此算的坐标会点空
  （`grab_window` 保留着，只适合「看一眼窗口长啥样」）。
- 裁切公式：`GetWindowRect` 拿窗口矩形，`GetClientRect` 拿客户区大小，
  `ClientToScreen(hwnd, (0,0))` 拿客户区在屏幕上的原点。

### 10.3 找窗口：标题匹配会误选 BepInEx 控制台

游戏窗口标题就是 `Territory`，但 **BepInEx 控制台窗口标题是
`选择 BepInEx 6.0.0-be.752+… - Territory`，也含 "Territory"**，按标题子串取第一个会选到它
（症状：客户区读到 960×480，所有点击/截图全打在黑框控制台上）。
`find_window()` 现在显式排除标题含 `BepInEx` 的窗口。

### 10.4 自动化友好的 mod 侧设计

- **窗口自报坐标**：`FacilityWindowUi` 在详细模式下打印
  `选择条屏幕坐标=x,y 客户区=WxH`（`WorldToScreenPoint` + y 翻转）。
  ⚠ 游戏窗口分辨率会变（实测同机出现过 1440×1080 / 1440×900 / 2560×1417），
  所以同时报出分辨率，测试端按比例换算（`e2e.to_client_coords`）。
- **F8 测试钩子**：`FacilityComponent.PollTestHotkey` → `FacilityWindowUi.TestClickSelector`，
  用 Unity 原生事件系统 `ExecuteEvents.Execute(bar, data, pointerClickHandler)` 派发点击。
  这条路**完全不依赖 OS 坐标标定**，是「按钮 → 写 cfg」链路最稳的验证方式
  （对应 e2e 里的「F8 测试钩子」一项）。
- 判「点击到底有没有生效」不看截图感觉，**读 cfg 文件**（`额外产品` 是否被改写）。

### 10.5 常见故障

| 症状 | 处置 |
|---|---|
| 启动后 e2e 说「游戏窗口不存在」 | 游戏还在加载，重跑一次 |
| HTTP 端口能连但不回包 | **游戏主线程卡死**（实测遇到过），e2e 会检测到并自动重启游戏 |

### 10.7 两条用血换来的自动化铁律

1. **不要按 ESC。** ESC 是暂停菜单开关，菜单第 6 个按钮就是「退出」；
   「盲按 ESC + 随后点屏幕中间」迟早点到退出（实测真的点退了一局，卡在「正在结束游戏。。。」）。
   现在的 `close_overlays()` 只关 UnityExplorer（F7），**不碰 ESC**。
2. **不要用像素判据认暂停菜单。** 试了三版：第 1 版按「金色长条」判 → 60+ 张世界截图全误报
   （木墙/木地板也是暖色）；第 3 版加了「多条等宽对齐」→ 又把**「参数设置」窗口**误判成暂停菜单
   （它也有 6 个金色描边按钮，只是更窄）。**从源头避免比事后识别划算得多。**

> 同理：**读档前一定要留缓冲**（`settle≥10s`），**启动游戏时一定要关系统代理**（§11）。

## 11. 系统代理会让游戏卡死在「加载中」（2026-09-13 踩到，排查花了很久）

**症状**：从主菜单进档后永远停在黑屏「加载中，请稍候…」，`inSave` 永远是 false，
`saveLoads` 不涨，等 4 分钟也没用；但游戏进程活着、HTTP 还能回 `state`。

**根因链**（在 `AppData\LocalLow\Looming\Territory\Player.log` 里找到的）：

```
Curl error 35: Cert verify failed. Certificate could not be verified ... UnityTls error code: 7
NullReferenceException: Object reference not set to an instance of an object.
  at BatchSpriteRendererHelper..ctor (UnityEngine.Camera c, List`1[T] sprite_atlas_handler_list)
  at MainScene.Start ()
```

1. 本机长期开着代理（FlClash，系统代理 `127.0.0.1:7890`，带 HTTPS MITM）
2. 游戏的 **Steamworks UGC 查询**（创意工坊订阅）走 UnityTls 做证书校验 → 被 MITM 证书拦下 → `Curl error 35`
3. 工坊 mod 的贴图因此没注册进 **sprite atlas**
4. `MainScene.Start()` 里 `new BatchSpriteRendererHelper(camera, sprite_atlas_handler_list)` 拿到空的
   handler 列表 → NullReferenceException → 世界初始化中断，UI 永远停在「加载中」

**解法 / 规矩**：

```python
st = A.proxy_off_for_launch()   # 关系统代理（会返回原状态）
A.launch_game(...); A.load_save()
A.restore_system_proxy(st)      # 世界进去后可以还原（工坊内容已挂载在内存里）
```

`_tools/e2e.py` / `test_appearance.py` 已内置这套开关。

> ⚠ 另一个**独立的坑**：AI 在 push 代码时给 shell 设过 `https_proxy`，
> 那会被子进程继承、同样毒化游戏进程。`autotest.launch_game()` 现在会**过滤掉
> `http_proxy/https_proxy/all_proxy/no_proxy` 再启动游戏**。
>
> 👉 **教训**：AI 为了 git push 设代理时，一定要用「只作用于这一条命令」的形式
> （`$env:https_proxy=...; git push` 这种会污染后续所有子进程），
> 并在事后清掉；否则会给游戏/构建留下莫名其妙的故障。
