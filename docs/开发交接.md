## 2. 环境、构建、部署（照做即可）

### 2.1 构建

```bash
cd /c/AI/mod/Facility
MSBuildEnableWorkloadResolver=false dotnet build -c Release
```

> ⚠ **`MSBuildEnableWorkloadResolver=false` 必须加**：这台机器 `dotnet` SDK 10.0.202 的
> 工作负载清单损坏（`工作负载集版本 10.0.203 缺少清单`），不加这个环境变量会直接 MSB4242 报错。
>
> ⚠ **不要用 `| tail -2` 之类的截断看构建输出**——本次开发中因此连续多次「以为构建成功、
> 实际全程编译失败」，DLL 停在旧版本，白白排查了很久。至少 `grep -E "error|个错误"`。

构建后 csproj 的 `PostBuild` 目标会自动复制 DLL 到 `C:\TerritoryModTest`。

### 2.2 部署链路（关键）

```
构建 → C:\TerritoryModTest\Facility.dll + Defs\*.json
        ↓ 游戏启动时「镜像同步」
     BepInEx\plugins\1006\Facility.dll + Defs\*.json
```

- `C:\TerritoryModTest` 是**游戏自带的本地测试目录**，启动时把整个目录镜像进 `plugins/<某个槽位>`
  （本项目实测是 **1006**；`1005` 是创意工坊版 JianZhu 的槽位）。
- **直接放 `BepInEx\plugins\自建文件夹` 会被游戏启动时删掉**，必须走 TerritoryModTest。
- 镜像同步发生在**游戏启动时**，所以改 DLL/Defs 后必须**重启游戏**才生效（Defs 也是，见下）。

### 2.3 改 Defs 后怎么生效

- Defs 是**进存档时**由 `D.LoadData` 读取的 → 改完 Defs 后**重新进入存档**即可，不必重启游戏。
  （但建造菜单 `BuildMenuGroup` 的装配是进程启动时做的，**动了 tech.json 必须重启游戏**。）

### 2.4 自动化进存档（开发效率关键）

游戏内装了 ChestEditor（本地 HTTP 服务 8765），可远程读档：

```bash
NEWEST=$(ls -t "/c/Users/c/AppData/LocalLow/Looming/Territory/TerritoryArchive/UserData" | grep ^2026 | head -1)
curl -s -X POST http://localhost:8765/api/editor/debug/load \
  -H "Content-Type: application/json" -d "{\"dir\":\"$NEWEST\"}"
```

> 用户要求：**每次都进最新的那个存档**（按 mtime 取）。
> ChestEditor.dll 需要放在 `TerritoryModTest` 里以便被镜像。

### 2.5 重启 + 读档 + 看日志 一条龙

```bash
tasklist | grep -i "territory.exe" | awk '{print $2}' | while read pid; do taskkill //PID $pid //F; done
sleep 3; start "" "steam://rungameid/1455910"
for i in $(seq 1 15); do sleep 10; curl -s -m 2 -o /dev/null http://localhost:8765/ && break; done
sleep 20
curl -s -m 8 -X POST http://localhost:8765/api/editor/debug/load -H "Content-Type: application/json" \
  -d "{\"dir\":\"$(ls -t "/c/Users/c/AppData/LocalLow/Looming/Territory/TerritoryArchive/UserData" | grep ^2026 | head -1)\"}"
sleep 45   # 等存档加载完
```

日志：`BepInEx/LogOutput.log`（mod 日志）、`AppData/LocalLow/Looming/Territory/Player.log`（Unity 异常）。

## 3. 逆向结论：这个游戏的 Mod Def 体系（**最重要的一节**）

游戏的官方 Mod 通道：`BepInEx/plugins/<任意文件夹>/Defs/<表名>.json`，
文件名（去扩展名）= 表名，内容是 JSON 数组，和官方表同一个加载器解析。

**关键教训：一座新建筑光有 stuff+build 是远远不够的。** 我们逐个撞出来缺什么：

| 表 | 缺了会怎样 | 必填要点 |
|---|---|---|
| `stuff.json` | 物品/设施不存在 | `stuff_id`、`prefab`、`stuff_img`、`stuff_img_on_map`、`effect_value` |
| `build.json` | 建筑不存在 | `id`、`class_name`(如 `FacilityGatherersHut`)、`cellw/cellh`、`menu_group`、`have_worker` 等 |
| `tech.json` | **建造菜单里完全不显示** | `txt_id` 是**分类段号**，必须与 `menu_group` 配对（见下） |
| `career.json` | **窗口没有工人控件、永远分不到工人** | 每个 `data_id` 组里 `is_main_facility` 只能有一个为 1 |
| `blueprint.json` | **窗口整个退化成占位值 + 主循环每帧抛异常** | 产品行 `product_id` + `formula_id`（官方惯例 `product_id*100+序号`） |

### 3.1 tech.json 的 `txt_id` = 分类段号

实测段号与 `menu_group` 的对应关系：

| txt_id | menu_group | 分类 |
|---|---|---|
| 100 | 0 | 初始 |
| 200 | 1 | 住所 |
| **300** | **2** | **食品**（本项目用） |
| 3700 | 3 | 制造 |
| 1500 | 4 | 物流 |
| 600 | 7 | 路桥 |

`tech_id=0` = 免科技。用错段号 → 建筑不出现在目标分类（我们一开始抄大通铺用了 200，菜单里死活找不到）。

### 3.2 career.json = 工人系统总开关

- 游戏里 `Facility.GetOriginalWorkPosCount` 会查 `D.career_dic_with_facility_id_as_key[stuff_id]`，
  查不到 → 工位数 0 → 窗口不渲染工人区、永远没人来（我们最初窗口就是个只读模板）。
- `npc_type` 决定职业（8=采集者）。多设施共用同一职业是**官方常态**（两块农田共用一个 farmer），
  所以我们直接复用采集营地 105006 的采集者职业行。
- ⚠ **`is_main_facility`：同一 `data_id` 组里只能有一个主设施**。
  我们照抄的行也是 1 → 采集者职业出现两个主设施 → 人手 DB 混乱（当时表现为窗口 99/99 不可交互）。
  必须置 **0**。
- `manpower_limit` 是基础工位数，但实际"原始工位数"被我们用 Harmony 补丁接到 cfg 了（见 §4）。

### 3.3 blueprint.json = 产品记录 / 数据键总开关（最阴的一个）

`FacilityHuntingCabin.GetProductDataKeyList(stuff_id)` 会按设施 id 查蓝图字典，**缺行直接抛 KeyNotFoundException**。

这一个异常会连锁炸掉：
- `WindowWorkFacility.SetInfo` 整条绑定链 → 窗口全变预制体占位值
  （工人数 99/99、库存空、今年/去年产量是假数据「原木四字 98」）
- `FacilityWork.IsReachLimit` 在 `NpcTaskHelper.Tick`（主任务循环）里**反复抛** → 工人领不到任务

我们加了 604001/605001 两行后，以上全部恢复正常。
**新建筑只要 `have_worker` 且想有产出，就必须有 blueprint 行。**

## 4. 代码结构

| 文件 | 职责 |
|---|---|
| `Plugin.cs` | 入口。绑定 cfg、注册 `FacilityComponent`、`PatchAll()`。含 `LogV`（详细日志门控）、`ParseProducts`、`ParseExtraCandidates`、`SetExtraProduct` |
| `FacilityComponent.cs` | 主线程服务循环（1.5s）：Reload cfg → 检测换日（`Clock.Now`）→ 每座建筑按 `工人数 × 产出表` 调 `Facility.AddStuff` 入袋 |
| `FacilityWorkPosPatch.cs` | Harmony Postfix `Facility.GetOriginalWorkPosCount`（仅 105040）→ 返回 cfg「每座最大工位数」，使窗口 +/- 可调人数 |
| `FacilityWindowUiPatch.cs` | 挂 `WindowGatherersHut.SetInfo` + `UpdateState`/`ShowWindowTip` → 调 `FacilityWindowUi.Apply` |
| `FacilityWindowUi.cs` | 窗口 UI 定制：改写文案 + 构建/刷新「额外产品」选择条（原生 uGUI `Button`，点击循环） |
| `Defs/*.json` | 5 张表（stuff/build/tech/career/blueprint），**由脚本生成，不要手改** |
| `_tools/make_defs.py` | 从官方表 `C:\AI\领地部分源码(AI注释)\ExtraData` 拷贝模板行生成 Defs；`--deploy` 部署到 `C:\TerritoryModTest\Defs` |

### cfg 键

```ini
[生产]
每人每日产出 = 604001:10,605001:10      # 物品id:每人每日数量，逗号分隔
每座最大工位数 = 10                       # 窗口 +/- 上限（1-25）
额外产品候选 = 616001:铁矿,616002:秘银矿,612001:红宝石
额外产品 = 0                              # 0=无；由窗口选择条写入
额外产品每日数量 = 10
[调试]
日志详细模式 = false                      # 打开后 LogV 的详细日志才输出
```

### 关键游戏 API（本项目已实测可用）

```
Clock.Now.Year / .MonthInYear / .DayInMonth     # 游戏日历（换日检测）
Facility.stuff_id / .guid / .is_build_finished / .npc_list  (List<Npc>，工人表)
Facility.AddStuff(stuffId, count)               # 入袋（搬运工会自动入库）
Facility.GetWorkPositionCount / GetOriginalWorkPosCount / GetWorkerNpcCount
D.Ins.career_dic_with_facility_id_as_key        # 职业表（工人系统）
WindowGatherersHut.SetInfo / UpdateState / ShowWindowTip
```

窗口内已知控件名（勘察得来，用于 UI 定制）：
`txt_forest_coverage_rate`、`txt_tip`、`txt_title`、`txt_num`、`txt_this_year`、`txt_last_year`、
`txt_this_manpower`、`txt_str`；容器 `content_area`；`window_prefab = window_gatherers_hut`。

## 5. 调试方法论（下次直接用这些招）

按「性价比」排序：

1. **先翻 `Player.log` 找 C# 异常堆栈** —— 本次最有效的一招。
   窗口诡异（数值不对/不能交互/功能缺失）时，异常堆栈会直接告诉你哪个方法炸了。
   ```bash
   grep -a -n "Exception\|was not present" /c/Users/c/AppData/LocalLow/Looming/Territory/Player.log | tail
   ```
   👉 **教训：现象是「UI 显示默认值」时，不要猜配置，先找异常。**

2. **写一次性「侦察补丁」dump 运行时结构**。例如本次 dump 出窗口里全部 TMP 文本名+内容、
   Button 列表（名字/位置/尺寸）、Dropdown 数量 —— 一步就知道有哪些控件可以改。
   代码模式：Harmony Postfix + `GetComponentsInChildren<T>(true)` + `Plugin.LogV`。

3. **射线探测判遮挡**：用 `EventSystem.RaycastAll` 在目标屏幕坐标打一发，打印命中对象。
   本次据此确认「下拉框没被遮挡，点击就是命中了它自己」，从而排除了布局问题、锁定输入派发问题。

4. **用「读文件」做客观验证**：UI 点击是否生效，不要只看截图——直接读 cfg 文件是否被写入。

5. **反编译语料库**（伪 C，函数名+调用关系齐全，非常好用）：
   - `C:\AI\游戏向量库\code_meta.json` —— `[{file, content}]`，按文件名查找函数实现
   - `C:\AI\领地部分源码(AI注释)\ExtraData\*.json` —— **官方数据表**（stuff/build/tech/career/blueprint/…）
   - interop 程序集字符串扫描（找字段/方法名）：
     ```python
     re.findall(rb'[A-Za-z_][A-Za-z0-9_]{4,60}', open(r'...\interop\Assembly-CSharp.dll','rb').read())
     ```
   - UnityExplorer 也在游戏里（但注意它和游戏都抢 F7）

6. **ReflectionTypeLoadException 的坑**：`Assembly-CSharp.dll` 反射时依赖没加载会全类型失败，
   不如直接扫二进制字符串。

## 7. 踩坑清单（省下重走的时间）

| 坑 | 症状 | 原因/解法 |
|---|---|---|
| **构建静默失败** | 改了代码毫无效果 | 用 `tail -2` 看输出截掉了错误行；DLL 一直是旧的。**必须完整看构建输出** |
| `dotnet build` MSB4242 | 工作负载清单损坏 | 加 `MSBuildEnableWorkloadResolver=false` |
| 建筑不进建造菜单 | 菜单里找不到 | 缺 `tech.json` 或 `txt_id` 段号与 `menu_group` 不配对（§3.1） |
| 窗口没工人控件 | 工人区完全不显示 | 缺 `career.json`（§3.2） |
| 窗口 99/99 不可交互、库存空、假产量 | 全部显示默认值 | 缺 `blueprint.json` → `KeyNotFoundException` 炸断 SetInfo（§3.3）。**先看 Player.log** |
| 工人不来 | 有控件但没人 | `is_main_facility` 冲突；或工位数 0 |
| `Transform.Find` 找不到子节点 | 每帧重复创建控件 | `Transform.Find` 只找**直接子节点**；用 `GetComponentsInChildren` 递归查找 |
| Unity `Dropdown` 点不开 | 控件可见、射线命中自身、就是打不开列表 | 游戏疑用自定义输入派发。**改用 `Button` 循环选择条一次通过** |
| Unity 字符串搜二进制搜不到 | grep DLL 找不到新字符串 | .NET 字符串是 **UTF-16** 存储，ASCII grep 无效；改用文件时间/大小判断是否更新 |
| 直接放 plugins 被删 | mod 消失 | 必须放 `C:\TerritoryModTest` 让游戏镜像 |
| Defs 改了没生效 | 老数据 | Defs 在**进存档**时读；tech.json 改动要**重启游戏** |
| IL2CPP 委托/构造差异 | CS1660 / CS1503 编译错 | 用 `DelegateSupport.ConvertDelegate<T>(new Action(...))`；`new GameObject(name)` + `AddComponent<RectTransform>()` 代替带组件构造 |
| 命名空间冲突 | CS 报错 | `using Foundation;` 会带来冲突；类名 `Facility` 与游戏同类冲突，项目用 `FacilityMod` |

## 8. 硬规则

- **文件编码**：UTF-8 无 BOM，换行 LF（`write_text(..., newline="\n")`）。
- **所有 IL2CPP 对象操作必须在主线程**（本项目走注入的 MonoBehaviour `Update`）。
- **不要用会截断的工具看关键输出**（构建/日志）。
- 开发测试**走 `C:\TerritoryModTest`**（镜像通道受保护），不要往 `BepInEx\plugins` 自建目录扔东西。
- 用户是中文交流；代码注释也写中文（现有代码风格如此）。
- 提交信息：中文、写清「改了什么 + 为什么 + 实测结论」。
- **GitHub 推送**：远程 URL 里带用户名（`https://Clawdhub945@github.com/...`）以避免弹账号选择框；
  直连经常 `Connection was reset`，重试或走代理 `https_proxy=http://127.0.0.1:7890`。
